# SHAJRetailProducts V1 Security Acceptance Matrix

Status: **RELEASE CERTIFIED**

## Authority boundary

- Central owns tenant identity, roles/permissions, POS registration, branch/store trust, offline-grant signing, canonical recovery authorization and tenant PostgreSQL authority.
- POSService is a small offline edge runtime. It verifies Central-issued grants, persists only local derived/session state required for offline operation, and must never become a tenant/permission/key authority.
- Frontend is presentation/orchestration only. Central browser credentials remain HttpOnly-cookie based and local POS access remains bound to the packaged POS local session/machine boundary.
- Security work reuses already-certified Auth/Az, Store/Device, Inventory, Catalog, Database and Observability boundaries rather than introducing parallel security models.

## Residual risk disposition

- Runtime-reachable `nodemailer`, `puppeteer`, and `xlsx` advisories remain **accepted with mitigations for V1, not fixed**. Existing executable boundaries constrain SMTP configuration, keep Chromium sandboxing enabled in production, and bound/content-verify spreadsheet parser admission. Future compatible upgrades/replacements remain required maintenance work.
- The 79 structural SQL interpolation sites remain as reviewed legacy structures. They are not blanket string-safe by convention: exact site count, expression-family disposition, direct request-object rejection, and identifier allowlist/internal-generation acceptance are now executable gates. Any change forces renewed Security review.
- Operator PostgreSQL restore paths are intentionally outside tenant/browser/POS HTTP authority and remain governed by the certified Database Recovery runbook.

## Release decision

**V1 SECURITY RELEASE CERTIFIED — FREEZE EXCEPT FOR REAL DEFECTS.** Tenant/store/device isolation, browser and offline authentication boundaries, credential/secret defaults, CORS/cookies, rate limiting, production TLS/container/logging, upload/path trust, dependency residuals, dynamic SQL structure, recovery separation, and the consolidated three-repository Security gate are covered by executable acceptance. Future advisory upgrades and any new Security-sensitive configuration/query/upload surface require explicit follow-up review; they do not invalidate the bounded V1 residual-risk decision above.
